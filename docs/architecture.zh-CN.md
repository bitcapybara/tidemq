# TideMQ 架构设计草案

> 来源：`tidemq.pdf`，2026-10-19，共 9 页。以下是完整 Markdown 转写，保留原文的要求、候选方案、性能参考、限制和待决事项；仅调整标题、段落、列表及链接排版。原文中的“实现语言尚未确定”保留为历史记录，仓库初始化时已选择 Rust。

## 01 / 设计目标与决策边界

**云原生消息队列 · 架构设计草案 v0.1**

2026-10-19｜面向数据采集与流处理。本文是架构评审基线，不是已验证的实现、性能承诺或生产部署方案。

### 已确定的要求

高吞吐、低延迟，目标至少达到 Kafka/Pulsar 对应模式的性能水平；对象存储承载长期数据；元数据使用 Raft 并与数据节点分开部署。云上同地域跨三个可用区；支持本地单节点与内网多节点。

### 消息与运维语义

独立持久订阅、逐条 ACK；分区内稳定 offset。设计方向支持并行处理或按 key 串行处理。统一客户端入口， SDK 自动恢复；故障恢复以秒级为目标。最低保留时长与未确认积压保护并用，超限不自动丢弃消息，限制新写入，继续消费、ACK 和回收。

### 推荐实现，仍需验证

计算 Broker 与 WAL 存储池分离；Gateway 可独立部署或与 Broker 合并。自建三副本数据 Raft 为基准后端，云共享 WAL 后续适配。第一版只在同一数据复制组内跨分区合装对象。分区由单个消费者实例持有，SDK 控制实例内并发。

### 尚未确定

实现语言、网络协议、云厂商、硬件与成本预算；实际消息大小与流量分布、分区/订阅规模、保留时长与积压配额；重试上限、死信策略、去重有效期、在线分区拆分与跨地域容灾。历史项目 Comet 是否作为代码基础也未确认。

### 评审原则

每个状态只有一个提交权威；超时不代表未提交；生产 ACK、消费 ACK、对象发布、WAL 回收是四个不同的完成点。

## 02 / 分层架构与部署

### 接入与数据路径

客户端 SDK → 固定域名 / 四层负载均衡 → Gateway → Broker → WAL 数据复制组。后台将已提交数据上传对象存储。元数据集群提供配置和路由，不转发消息正文。

### Gateway / Broker

Gateway 终止消息协议连接、鉴权、缓存路由、转发与排空；不拥有唯一持久消息状态。Broker 负责写入协调、订阅分发、缓存和流控。故障后从持久化状态恢复，不能承诺连接永不断开。两个角色可以组合启动以减少部署负担。

### 元数据 Raft

维护 Topic、分区到数据组映射、节点拓扑、所有权 epoch、订阅配置、对象清单与生命周期。生产先用三个投票节点，跨三区；高频数据追加和逐条 ACK 不进入这一全局组。扩大同一 Raft 组的成员数不能替代元数据分片。

### WAL 存储池

多个独立复制组并行工作；每组可承载多个逻辑分区，三个副本分别位于三个区。一台存储节点可以承载多个组。数据组提交消息、offset、生产者去重、writer fence 与发布意图。副本配置变更使用受验证的共识成员变更协议。

### 持久订阅状态

消费状态按订阅/分区分片，使用复制日志和检查点；可复用存储基础设施，但与全局控制元数据隔离。必须指定 ACK 权威分片，不能让多个 Broker 各自在内存确认同一投递。

### 本地与云上

单节点：各角色组合运行，复制因子 1，无节点高可用。内网多节点：独立目录和节点身份，默认三副本，连接共同可访问的对象后端；各机器私有目录不能充当共享对象存储。同机多进程仅验证进程故障。云上：元数据、计算、存储独立资源池，跨区放置与容量预留。单节点模式不作为生产故障时的隐式降级。

## 03 / 消息、订阅与客户端契约

### 消息身份

对外 message_id 建议包含 topic 的不可复用身份、partition_id、offset；删除重建 Topic 不复用原身份。消息 key 决定分区路由；不承诺跨分区全局顺序。迁移服务节点不改变消息身份。

### 生产幂等

批次携带 producer_id、producer_epoch、分区内 sequence 和内容摘要。去重结果与消息在同一数据组提交，重复请求返回原 offset/结果；相同身份和序号但不同内容必须报冲突。明确序号缺口、窗口大小与去重过期后的行为。

### SDK 重试边界

网络重连保留批次身份。SDK 进程重启若没有持久化未决批次及生产者状态，不能无条件保证跨重启去重；业务事件 ID 或本地持久队列可作为额外机制。只有服务端持久化提交才返回生产成功。

### 逐条 ACK

订阅保存连续确认前沿和前沿之后的已确认区间/位图。逐条语义允许批量传输与持久化；提供可等待服务端持久化的确认结果，区分本地入队与完成。ACK 丢失时重试幂等，旧投递令牌不能确认新的投递尝试。

### 并行与顺序

并行模式允许乱序完成。按 key 模式由 SDK 对同 key 串行执行，不同 key 并行；失败时阻塞后续同 key，除非明确允许跳过。该保证不覆盖旧消费者失联后仍继续写外部系统，外部副作用需要幂等、版本约束或 fencing。

### 消费接管

新的订阅分配代次隔离旧会话，恢复持久 ACK 状态后重新投递未确认范围。在途投递信息需要持久化或采用可证明安全的保守重投方案；首版优先正确性。默认至少一次交付，不宣称外部业务 exactly-once。

### 有界状态

限制每订阅/分区在途消息数、字节数和 ACK 空洞窗口。慢消息不可无限扩大位图和重试队列。永久失败、死信与人工跳过策略仍需确定；默认不能为了清空积压自动当作已处理。

## 04 / 写入链路与提交边界

### 正常写入

1. SDK 批量发送，Gateway 按缓存路由转发。
2. Broker 携带所有权 epoch 提交数据组。
3. 数据组串行检查 fence、去重与序号，并确定 offset。
4. 正文和恢复信息复制落盘，满足 Raft 提交规则。
5. 返回 offset，生产 ACK 完成；消费者只见已提交消息。

### 三个逻辑边界

统一采用排他上界：committed_end 是下一条未提交 offset；object_published_end 是连续完成对象发布范围的末端；local_reclaim_end 是本地消息数据可回收边界。始终满足 local_reclaim_end ≤ object_published_end ≤ committed_end。

### 不要混淆索引

消息 offset 与 Raft log index 不同。数据组还复制 fence、发布任务等记录；消息可回收不等于共识日志可以立即截断。未提交的消息 offset 可在恢复后重新分配，但绝不能把其记录或成功结果暴露给客户端。

### 快照与日志压缩

快照至少包含下一 offset、已提交范围、fence、生产者去重和原结果、对象映射/代次及未完成发布状态。快照必须可校验、可安装并持久化后再压缩对应共识日志。新副本可由快照、对象数据和必要日志尾部恢复。

### 写入吞吐

使用批量追加、group commit、流水线复制、有界队列和零/少拷贝设计。批次同时受大小与等待时间限制。数据组数、活跃分区数与副本组映射按压测决定，不预设每分区必须独占一个 Raft 组。

### 故障结果

提交前失败：允许重试，不能声称已成功。提交后响应丢失：同身份重试返回原结果。丢失多数派：停止确认新写入，不能降副本数绕过安全条件。一个区故障后继续服务的前提是剩余多数派、入口和资源均可用。

## 05 / 分区所有权与故障接管

### 状态路径

ACTIVE → TAKING_OVER → FENCED → RECOVERED → ACTIVE(new epoch)。这是协议草案的逻辑状态，不要求直接照抄成数据库枚举。每次迁移有唯一操作 ID，状态迁移必须具备前置条件与幂等性。

### 控制权与写入权

元数据 Raft 分配递增 epoch 并指定新拥有者；数据组通过共识提交安装该 fence。数据组只接受已授权的新 epoch，拒绝更低 epoch，不能允许任意请求者自行抬高 epoch。

### 恢复后才发布路由

新 Broker 等 fence 提交，获取权威提交状态与检查点，恢复生产者和订阅必需状态，然后以条件更新激活路由。陈旧 Gateway 路由可能暂存，但旧写入在数据组被安全拒绝。

### 迁移中的宕机

分配 epoch 后但 fence 前：不得宣布新主可写。fence 后但路由激活前：后续拥有者完成或以更高 epoch 取代。旧请求若先于 fence 合法提交，保留结果；fence 后不能接受旧 epoch 的新追加。

### 计划与故障

计划迁移提前预热缓存/状态、停止新分配、排空在途，再执行最终交接。故障恢复从持久化检查点与有限尾部恢复，不先下载全部历史。恢复服务和修复至完整三副本分别观测。

### 元数据不可用

明确降级边界：不做新分配、接管、配置变更和对象清单发布。现有拥有者可否继续读写，取决于 fence、权限和缓存有效性契约；不能隐式假设元数据停机时仍可无限续租。首版需故障矩阵验证，并在无法证明安全时停止相关操作。

### 秒级目标

规划内迁移通常 ≤1 秒、单 Broker/Gateway 故障 P99 ≤5 秒、单区故障 P99 ≤10 秒为候选设计/压测目标，不是 SLA。测量从故障发生到受影响客户端成功恢复；入口检测、选主、fence、恢复、路由和 SDK 重连均计入。

## 06 / 对象发布、整理与回收

### 对象布局

低流量分区合装，大流量分区独立对象。第一版只在同一数据复制组内合装，不跨组汇聚。对象不可变且身份唯一，携带各分区 offset 范围、块位置、版本和校验信息；支持范围读取。

### 对象状态

REGISTERED → UPLOADED → PUBLISHING → PUBLISHED → DELETING → DELETED。上传前登记任务与对象；只上传已提交消息。消息可读的对象引用以已提交清单为准，不能通过扫描桶列表推导。

### 跨数据组/元数据组的提交

数据组记录持久发布意图，绑定对象、范围、所有权 epoch、操作 ID、预期清单代次；元数据按条件幂等应用引用变更；数据组再记录发布完成。这里不是跨服务原子事务，必须能对账并恢复每个中间态。

### 待发布任务也保护对象

元数据登记任务必须先于数据授权，并与删除状态串行化。回收前需要取得不可再发布的终止结论；不能仅因 RPC 超时或任务年龄大就删除。若一方不可用或结果不确定，保留对象和必要日志，允许暂时泄漏空间，禁止冒险误删。具体终止/撤销协议是实现前评审阻塞项。

### 清单竞态

旧 epoch 不得新增发布授权，但已经合法提交的发布意图可能需要由恢复者完成。清单代次冲突时做恢复对账，不能盲目覆盖新状态。范围重叠、重复发布、部分完成与对象内容不一致必须被检测。

### Compaction 与 GC

对象整理先生成并验证替代对象，再原子切换受影响清单引用。旧对象需等待读取、恢复任务和快照的有效 pin、全部引用及待发布任务解除；租约式 pin 到期后，任务必须停止旧视图并重新获取。DELETING 禁止新增引用，删除调用可重试；对象 ID 永不复用。对象整理不等于按 key 丢弃历史版本。

### 本地回收

发布成功后还需存储组持久记录、恢复检查点与副本追赶条件满足，才回收本地正文。对象上传失败使 WAL 积压，达到水位必须背压；容量需覆盖目标中断窗口及副本开销，不能将稳态小 WAL 容量当成故障期容量。

## 07 / 保留策略、弹性与统一入口

### 正常逻辑回收

消息超过最低保留时长，并且所有需要保护该消息的持久订阅均已确认，才满足普通回收条件。新建订阅只能从仍保留的数据开始；订阅创建、删除、seek 与回收边界必须协调，不能让新订阅追溯“复活”已回收消息。

### 超限处理

默认告警并限制/拒绝受影响 Topic 的新写入，不自动丢弃未确认消息。消费、ACK、GC 保持可用；SDK 缓冲有界。降至低水位后恢复写入，使用迟滞避免抖动。配额同时区分逻辑积压、物理存储及共享对象造成的回收滞后。

### 单一逻辑地址

固定域名指向跨区四层负载均衡，后接多副本协议 Gateway。SDK 无需维护内部节点列表，但可自动使用多条连接。Gateway 隐藏后端路由切换；Gateway 本身故障仍需要 SDK 重连、恢复会话和幂等重试。

### 请求期限

所有自动恢复受总 deadline、重试预算与背压约束；超过预算返回明确错误。连接保持不等于请求已提交，网关不能自行确认消息。区分可重试、已隔离、鉴权失败、配额受限和结果未知等错误。

### 计算扩缩容

Gateway 扩容主要承接新连接；旧长连接不会自动均衡，需受控重连。Broker 扩容迁移服务所有权，避免迁移历史正文。缩容先停止新分配、排空、移交再退出。

### 存储扩缩容

扩容优先放置新组/新数据，热点必要时限速迁移。缩容先修复/迁出副本，安全变更成员后退出；不能当无状态实例直接删除。限制并发修复与迁移，维持跨区放置和故障容量余量。

### 读取与自动均衡

热读缓存和历史块缓存隔离，范围请求合并与预取，单独限制回放、修复、Compaction 带宽。均衡考虑字节率、CPU、连接、ACK 状态等，带冷却时间和迁移成本；逻辑分区拆分另行设计。

## 08 / 性能基线与验证路线

### 对标原则

目标至少达到 Kafka/Pulsar 对应模式水平。比较完整计算、WAL、对象请求和网络成本，并对齐持久化、批量、压缩、分区、订阅与顺序语义。报告可持续吞吐、生产 ACK 与端到端 P50/P99/P99.9、积压增长和资源利用率。

### AutoMQ 官方参考，不是本系统实测

2026-01-14 FSxN 报告：3 台 m7g.4xlarge 服务端，另有 3 台客户端，FSx 736MB/s、1TB SSD、3072 IOPS。 1KiB 消息、64KiB 批次、linger 3ms，写入 300MiB/s（307200 条/秒），四路消费聚合约 1.2GiB/s；写入平均 7.89ms / P99 16.30ms，端到端平均 9.88ms / P99 22ms。

### 基线限制

报告使用 FSx WAL、acks=1、RF=1 和消费自动提交，不是本系统自建三副本 + 逐条持久 ACK。正文 96 分区与展示片段 32 分区需核对完整脚本。低于 10ms 是平均值而非 P99；稳态数字不证明故障恢复时间。该工况是建议参考，尚非最终容量承诺。

### 测试矩阵

覆盖小/中/大消息、压缩开关、多个批次等待值、多个分区和订阅数；追尾与冷回放；乱序 ACK 空洞、慢订阅、消费者重启；Broker/Gateway/WAL 故障、单区隔离、扩缩容、对象存储延迟与不可用。以相同版本和公开配置可复现运行。

### 正确性必须优先通过

校验已确认消息在故障模型内不丢、offset 不串消息、重复生产得到原结果、旧 epoch 被拒绝、持久 ACK 不回退、对象不提前删除。注入每个持久化步骤前后的宕机，并测试响应丢失与重试。

### 分阶段实施建议

阶段 A：协议模型与确定性故障模拟；阶段 B：本地最小完整链路；阶段 C：三节点复制、去重、ACK 与恢复；阶段 D：对象合装/发布/GC；阶段 E：Gateway 与扩缩容；阶段 F：三可用区对标及故障验收。各阶段以安全性和可观测性过关后再优化吞吐。

### 实施前仍需决策

确定语言/共识库/协议、元数据与数据状态边界、发布终止协议、ACK 投递令牌规则、去重有效期、保留与配额值、对象大小/上传间隔、快照频率，以及部署成本预算。本草案不授权创建付费资源或修改现有项目。

### 重点评审问题

1. 发布授权、取消和删除是否在所有竞态下安全？

2. 去重状态及原结果是否能跨快照、迁移、SDK 重启恢复？

3. ACK 已提交但返回丢失，旧投递重试是否安全？
