# 可选 OTLP 导出验证记录（2026-10-20）

环境为 Darwin arm64、Rust 1.96.0（`ac68faa20`），在独立 observability worktree 验证。以下结果是本机功能、故障与资源边界证据，不作为 Linux/三区性能或生产 SLO 验收。服务默认仍关闭 OTLP。

## 实际故障与链路

`tracing_export` 使用官方 OpenTelemetry protobuf 类型解码实际 HTTP 请求，验证父 span/trace ID、有限属性、无 event/link/tracestate，以及正文、token、任意 dependency 字段不进入导出。宿主已有自定义 subscriber layer 与官方桥接共存。

实际覆盖慢响应、503/Retry-After、大 Content-Length、无 Content-Length 的大 chunked 响应、Collector 关闭后恢复。导出并发为 1，排队和正在导出共用固定字节许可，失败丢弃可计数；恢复后的每次尝试仍保留配置间隔。外部 sampled 标记不能越过本地采样预算。

原始关闭期限回归以 20 ms 期限中止正在等待的导出，验证 abort 后 join、许可清零与明确 timeout 错误；空队列即使配置 5 秒导出间隔，也不为等待 interval 耗尽短关闭期限。自签 IP TLS 证书被拒绝；另一个真实 TCP peer 停在 TLS 握手阶段，50 ms export timeout 生效。直连导出只接受字面 IP，并使用编译内置根离线验证，避免 DNS 或平台信任联网工作逃逸期限。

`runtime_queue` 的追踪用例复用既有 Fixture，实际启动 Metadata、Storage、Broker、Gateway 四个独立 CLI 进程。由 SDK 宿主拥有 subscriber/exporter，验证同一 trace 的 SDK → Gateway → Broker 父关系和 owned producer submission 上下文。Collector 正常、慢、失败、超大响应、进程停止及恢复期间，各轮生产、读取与持久 ACK 均继续，offset 逐一推进；随后关闭客户端与四个服务进程。用例的 3 秒操作期限仅为功能故障防挂死界限，不是恢复或性能 SLO。

独立单元测试还验证观测 span 在原操作期限结束后释放，而 owned 业务 future 继续等待并返回后续权威结果，不能由追踪期限取消已提交业务。

## 官方 Collector

使用官方 core **0.162.0** Darwin arm64 二进制，来源为[官方 release](https://github.com/open-telemetry/opentelemetry-collector-releases/releases/tag/v0.162.0)，tar SHA256 为 `53de34c02913f54aa240861e0febf67a6839bc8ecf1bfab83a8ae7d355d30674`，与 GitHub asset digest 一致。没有把仅含 profiler 资产的其他 tag 当作 core 验证。

测试实际执行 `--version`、`validate`，使用仓库 [collector.yaml](../../deploy/observability/collector.yaml) 的动态 loopback 端口副本运行，发送官方 SDK/exporter 生成的真实 span，并从自监控确认 accepted span 至少为 1。SIGINT 正常退出返回 0，接收和自监控监听端口可重新绑定；未启用 SO_REUSEPORT 绕过退出检查。

实际自监控指标为：

- `otelcol_receiver_accepted_spans_total`、`otelcol_receiver_refused_spans_total`、`otelcol_receiver_failed_spans_total`；这些系列可能在首个请求前尚未出现。
- `otelcol_process_cpu_seconds_total`、`otelcol_process_memory_rss_bytes`、`otelcol_process_uptime_seconds_total`。
- `otelcol_process_runtime_heap_alloc_bytes`、`otelcol_process_runtime_total_alloc_bytes_total`、`otelcol_process_runtime_total_sys_memory_bytes`。

默认 `nop` exporter 接收后丢弃，发送队列、网络出口和重试均为 0，不打印 span 内容，不提供追踪搜索或持久存储。内存、HTTP body、batch 和超时限制由 YAML 显式给出。当前主机没有 Docker；native Collector 运行结果不代表 Compose 容器运行已经验证，profile 整合由主分支另行验证。

## API 依据与尚未覆盖

依赖版本和官方 API 链接见[运维文档](../operations/tracing.zh-CN.md)。先通过 crates.io metadata 核对 upstream，再查 versioned docs.rs；部分 docs.rs 访问不可用时，对照 Cargo 对应精确版本的 registry 发布源码。采样、span、HTTP exporter、protobuf 和 tracing 桥接来自官方库；自有薄 processor 只负责统一许可、owned Tokio 生命周期、速率和有限自监控，不实现 OTLP 协议。

尚需真实 Linux/cgroup、三区/负载均衡、长时压力与正式性能矩阵验证。未实测远端公网 IP SAN 证书成功路径或外部持久 trace 后端；首版不直连 DNS/私有 CA/mTLS/认证后端，可由本机 Collector 代理。逻辑 `pending_bytes` 不等于 RSS/allocator 上界，Collector accepted 也不等于后端持久保存。默认 1% 的本地采样与独立节点速率限制可能形成不完整 trace，不能用作审计或完整消息链路台账。
